\xchapter{Takeaways}

\begin{frame}{Five Things to Walk Out With}
  \begin{itemize}
    \item A car is a distributed computer, same bug classes as any software, plus a 2-tonne body attached.
    \item Your tutorial's fundamentals (assets, threats, risk, CIA) map straight onto ECUs, buses and the cloud.
    \item Regulation turned ``do your best'' into a mandatory, auditable engineering process.
    \item \alert{One unchecked \texttt{strcpy}} turned input into control. We did it live, in 20 lines.
    \item No single defence is enough, security is layers, from the compiler to the supplier contract.
  \end{itemize}
\end{frame}

\begin{frame}{Where This Can Take You}
  \begin{itemize}
    \item \textbf{Vuln research / pentesting} -- find today's bug before the attacker does.
    \item \textbf{Security engineering} -- bake TARA and secure design into the car from day one.
    \item \textbf{OS \& platform security} -- harden QNX/Linux ECUs (MAC, secure boot, sandboxing).
    \item \textbf{Security management / GRC} -- run the 21434 process, incident response, supplier security.
  \end{itemize}
  \vspace{1mm}
  \begin{alertblock}{Both halves of this room matter}
    The best automotive security engineers understand the \emph{physical} system they protect, not just the code on it. Mechanical and informatics, together.
  \end{alertblock}
\end{frame}
